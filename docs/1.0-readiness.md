# Aura 1.0 readiness

Stability is the first release priority. AI development accuracy, speed,
verifiability, low token use, and ease of learning are the second priority and
override every non-stability concern.

This checklist distinguishes repository evidence from external release state.
A checked item has an executable local or CI gate in this repository; an
unchecked item still requires authoritative external evidence.

## Runtime and AI contract

- [x] Explicit `AuraApp.create().use(...)` module composition and dependency graph.
- [x] Immutable validated configuration and deterministic lifecycle states.
- [x] Bounded executors, cancellation propagation, graceful shutdown, and
  observable cleanup failures.
- [x] One route metadata model for HTTP, TestClient, Schema, OpenAPI, MCP, and
  generated route code.
- [x] TestClient/Undertow parity for query encoding, header case, cookies,
  middleware, errors, and route binding.
- [x] Generated route metadata path, with handwritten `Route` contributions as
  the only alternative — no reflection-based route registration.
- [x] AI golden evaluation manifest and compile/TestClient loop.
- [ ] Measured evidence that staged context loading lowers token and repair cost while
  preserving stability. The gate exists, runs, and fails closed. `pilot-20261103`
  (n = 1 per arm, run ids `pilot-20261103-<task>-<arm>`) lowered prompt tokens by
  about 68% but cost a repair round on both tasks, lost final success on
  `route-authorization`, and spent 18,679 tokens against a 4,000 `maxTokens`
  budget, so it contradicted the claim. The first of the three responses was
  taken -- the staged recipe was fixed rather than the numbers edited:
  `28d8fc1` made the guide's `TestClient` examples compilable units carrying
  `import io.aura.web.TestClient;`, which is what the failing answers had been
  inventing. `pilot-20261104` (same tasks, both arms, repair cap 3 as the task set
  declares) then cut prompt tokens 84.2% with zero repair rounds and no lost
  first-pass or final success in either arm. It stays unchecked because two legs
  are still red: n = 1 per arm cannot size an effect, and the staged run costs
  9,641 tokens against a 4,000 `maxTokens` budget -- a budget no recipe that ships
  `AI_GUIDE.md` can meet, since its own first call is already about 8,100 prompt
  tokens. Next: restate that budget with a derivation before the cohort that is
  graded on it, then three samples per arm. None of it by editing the records or
  the thresholds after the fact.

Evidence:

```bash
bash scripts/verify-local-readiness.sh
```

`verify-local-readiness.sh` is the single repository-only verification entry
point. It intentionally does not trigger GitHub Actions, Docker/kind, external
database services, GPG production signing, or Central Portal publication.
The release-signature step has a 600-second Maven watchdog; local diagnostics
can shorten it with `AURA_RELEASE_VERIFY_TIMEOUT_SECONDS`.

To report external evidence without triggering any action, run:

```bash
bash scripts/report-readiness-evidence.sh
```

## Security and production boundaries

- [x] Snapshot redaction and bounded retention.
- [x] External HTTP target validation, timeout, cancellation, and response limits.
- [x] Credentialed wildcard CORS and WebSocket Origin rejection.
- [x] Trusted proxy, Host allowlist, TLS, request/body/upload/WebSocket limits.
- [x] Route/IP/API-key admission controls and bounded state.
- [x] Liveness/readiness with bounded dependency checks.
- [x] Undertow `2.3.21.Final` or newer secure baseline.
- [x] Full OSV scanning on pull request, push, and weekly schedule.

Evidence: `mvn verify`, security regression tests, and `.github/workflows/ci.yml`.

## Release gates

- [x] BOM, starter, archetype, executable JAR, Dockerfile, and Kubernetes template.
- [x] Public API classified report and reviewed baseline.
- [x] CycloneDX SBOM with complete 13-module closed dependency graph.
- [x] Ephemeral-key verification of all release artifact signatures.
- [x] SHA-256 manifest generated and verified for every release artifact and signature.
- [x] Maven `3.8.6` full-reactor verification job.
- [x] Docker/kind/server-side Kubernetes smoke is defined as a bounded CI job.
- [ ] GitHub-hosted Docker/kind deployment-smoke run confirmed green.
- [ ] GitHub-hosted PostgreSQL/MySQL service-container migration run confirmed green.
- [ ] GitHub-hosted Java 17/23, OSV, docs, API, SBOM, and minimum-Maven jobs
  confirmed green on the intended commit.
- [ ] Production GPG key signing verified without exposing private material.
- [ ] Central Portal staging deployment validated.
- [ ] Central Portal production publication explicitly authorized and completed.

An authorized maintainer can use the `workflow_dispatch` input on `.github`
Actions to run this matrix against the selected commit. The run name records
the reason, and the resulting artifacts are the authoritative evidence for the
unchecked GitHub-hosted items above. Local execution must not mark those boxes.

## Completion rule

Aura 1.0 is not release-complete while any unchecked release gate above lacks
authoritative evidence. Do not infer external CI or Central Portal success from
local tests. Do not run `deploy` or publish artifacts without explicit release
authority and credentials.
