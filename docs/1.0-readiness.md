# Aura 1.0 readiness

Stability is the first release priority. AI development accuracy, speed,
verifiability, low token use, and ease of learning are the second priority and
override every non-stability concern.

This checklist distinguishes repository evidence from external release state.
A checked item has an executable local or CI gate in this repository; an
unchecked item still requires authoritative external evidence.

## Runtime and AI contract

- [x] Explicit `AuraApp.create().use(...)` module composition and dependency graph.
- [x] Immutable validated configuration and deterministic lifecycle states.
- [x] Bounded executors, cancellation propagation, graceful shutdown, and
  observable cleanup failures.
- [x] One route metadata model for HTTP, TestClient, Schema, OpenAPI, MCP, and
  generated route code.
- [x] TestClient/Undertow parity for query encoding, header case, cookies,
  middleware, errors, and route binding.
- [x] Generated route metadata path, with handwritten `Route` contributions as
  the only alternative — no reflection-based route registration.
- [x] AI golden evaluation manifest and compile/TestClient loop.
- [x] Measured evidence that staged context loading lowers token and repair cost while
  preserving stability, inside the scope that was measured. `cohort-20261104-n3`
  recorded twelve runs -- `crud-module` and `route-authorization`, both arms, three
  samples per arm, `claude-opus-4-5` at `temperature: 0`, compiled at `986001a` -- and
  `scripts/verify-ai-evals.sh` passes on them: input tokens down 84.2% on both tasks
  (median 51,679 → 8,185 and 51,662 → 8,168), zero repair rounds in either arm, first
  pass and final success 3/3 in all four arms, worst staged record at 21% of its
  derived budget. The twelve generated sources hash twelve different ways, so the
  repetitions are distinct answers rather than one answer counted three times.
  Getting here is the part worth keeping: `pilot-20261103` (n = 1 per arm) refuted the
  claim -- 68% fewer prompt tokens but a repair round on both tasks and no successful
  `route-authorization` -- and the response was to fix the recipe rather than the
  numbers. `28d8fc1` made the guide's `TestClient` examples compilable units carrying
  `import io.aura.web.TestClient;`, which is exactly what the failing answers had been
  inventing, and `pilot-20261104` then showed the refuted half had been a
  documentation hole, not a property of small context. Its other red leg was the
  instrument: 9,641 tokens against a 4,000 `maxTokens` no recipe shipping
  `AI_GUIDE.md` could ever meet, since its first call alone is about 8,100 prompt
  tokens. `986001a` restated that budget as the worst declared cost of the experiment,
  with the derivation in `evals/README.md` and `AiEvaluationManifestTest` recomputing
  it from the declared context so it cannot be typed to fit a result, and that change
  landed *before* the cohort graded on it -- which stranded `pilot-20261104` by
  `taskSetHash` and is the price of the order being right rather than convenient.
  Nothing here was reached by editing a record or lowering a threshold in the change
  that declares victory. What the measurement does not cover: two of the ten manifest
  tasks, one model, one day. The claim is accepted for the tasks in that table, and
  the remaining eight are unmeasured.

Evidence:

```bash
bash scripts/verify-local-readiness.sh
```

`verify-local-readiness.sh` is the single repository-only verification entry
point. It intentionally does not trigger GitHub Actions, Docker/kind, external
database services, GPG production signing, or Central Portal publication.
The release-signature step has a 600-second Maven watchdog; local diagnostics
can shorten it with `AURA_RELEASE_VERIFY_TIMEOUT_SECONDS`.

To report external evidence without triggering any action, run:

```bash
bash scripts/report-readiness-evidence.sh
```

## Security and production boundaries

- [x] Snapshot redaction and bounded retention.
- [x] External HTTP target validation, timeout, cancellation, and response limits.
- [x] Credentialed wildcard CORS and WebSocket Origin rejection.
- [x] Trusted proxy, Host allowlist, TLS, request/body/upload/WebSocket limits.
- [x] Route/IP/API-key admission controls and bounded state.
- [x] Liveness/readiness with bounded dependency checks.
- [x] Undertow `2.3.25.Final` or newer secure baseline.
- [x] Full OSV scanning on pull request, push, and weekly schedule.

Evidence: `mvn verify`, security regression tests, and `.github/workflows/ci.yml`.

## Release gates

- [x] BOM, starter, archetype, executable JAR, Dockerfile, and Kubernetes template.
- [x] Public API classified report and reviewed baseline.
- [x] CycloneDX SBOM with complete 13-module closed dependency graph.
- [x] Ephemeral-key verification of all release artifact signatures.
- [x] SHA-256 manifest generated and verified for every release artifact and signature.
- [x] Maven `3.8.6` full-reactor verification job.
- [x] Docker/kind/server-side Kubernetes smoke is defined as a bounded CI job.
- [x] GitHub-hosted Docker/kind deployment-smoke run confirmed green.
- [x] GitHub-hosted PostgreSQL/MySQL service-container migration run confirmed green.
- [x] GitHub-hosted Java 17/23, OSV, docs, API, SBOM, and minimum-Maven jobs
  confirmed green on the intended commit.
- [x] `dependency-review` cleared: Undertow 2.3.25.Final and pgjdbc 42.7.12
  supersede the four high-severity advisories that held the gate open.
- [x] Production GPG key signing verified without exposing private material.
- [ ] Central Portal staging deployment validated.
- [ ] Central Portal production publication explicitly authorized and completed.

An authorized maintainer can use the `workflow_dispatch` input on `.github`
Actions to run this matrix against the selected commit. The run name records
the reason, and the resulting job statuses are the authoritative evidence for
the GitHub-hosted items above. Local execution must not mark those boxes.

GitHub Actions run `42159837307`, the `push` run of CI that `master` at
`b4051ad` triggered, is that evidence: `test (17)`, `test (23)`,
`minimum-maven`, `database-migrations`, `osv-full-scan`, `mcp-npm` and
`deployment-smoke` all reported success. `dependency-review` is a
`pull_request`-only job and is skipped on `master`, so its evidence is the
`pull_request` run `42145583090` on `52e45df`, the commit `b4051ad` merges.

Signing is the one gate no hosted run can prove, and it is proven without the
key leaving this machine: `mvn -Prelease -DskipTests clean install` signed the
reactor with the imported production key and `gpg --verify` on an installed
`.asc` reports fingerprint `E008AFD6011B7FE10E25073F78D8531C2CA83C3F` for
`io.github.tianhaocui`. The two Central Portal boxes stay unchecked because
publication is a decision, not a build.

## Completion rule

Aura 1.0 is not release-complete while any unchecked release gate above lacks
authoritative evidence. Do not infer external CI or Central Portal success from
local tests. Do not run `deploy` or publish artifacts without explicit release
authority and credentials.
